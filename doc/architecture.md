# Front-end architecture

Target structure. Folders are created when they're first needed, not
before.

## Layers

View → Components → Store / Composable → API layer → fetch

Dependencies only go in that direction: a component doesn't call `fetch`, and
`src/api/` imports nothing from Vue or Pinia.

## Folders

```
src/
├── api/          The only place with fetch. client.ts + one file per resource
├── types/        The back's contract types, generated by `npm run generate:types`; never edited by hand
├── stores/       Pinia: state shared by several views
├── composables/  Logic with local state
├── router/       Routes and guards
├── views/        One per route, lazy-loaded
├── components/
│   ├── ui/       Generic, no business logic
│   ├── layout/   App shell and layouts
│   └── <feature>/  One folder per feature
├── assets/
└── __tests__/
```

Folders are by type; reconsider folders by feature/domain if the project
grows to dozens of components.

## Rules per layer

- **views/**: thin. They read route parameters and compose components.
- **components/**: render UI. Props down, events up. They never call the
  API.
- **stores/**: state used by several views. Stores in _setup_ format. In
  components, read the state with `storeToRefs`. Pinia rather than a
  hand-rolled `reactive()` store; revisit only if the app stops needing shared
  conventions and Vue Devtools integration.
- **composables/**: logic with local state for one view or component. Rule:
  start local and move up to a store only when more than one view needs it.
- **api/**: plain TypeScript. Each function returns typed data or throws
  `ApiError`. It strips the `{ data }` envelope so stores receive the
  resource directly.
  - Errors: the back's contract (the error schemas in the generated types)
    defines their shape, and `client.ts` derives the error classes' fields
    from those schemas. `ApiError` is the base; each contract schema that
    extends it gets an `ApiError` subclass with the same name and its extra
    fields, and `client.ts` picks the subclass from the response's `code`.
    Logic branches on `code`, never on `status` or the text of `message`.
  - `code` is a closed type, but the back treats it as an open enum at
    runtime. `client.ts` checks the received code against the runtime array
    the generator emits, so the rest of the app can trust the type; an error
    the contract doesn't describe (unknown code, non-JSON body from something
    in between) becomes a front-only code and is logged with `console.error`
    so a developer knows to regenerate the types. A request with no response
    (`fetch` rejects) also becomes an `ApiError`, with status `0` and its own
    front-only code. Front-only codes are defined in `client.ts`, never in
    `src/types/`, and a compile-time check fails `npm run type-check` if one
    overlaps a contract code.
  - `client.ts` sends `Accept-Language` on every request; the back uses it to
    translate validation messages. It's fixed to Spanish until
    internationalization exists (see [Pending decisions](#pending-decisions)).
  - When writing a function, check in the generated types which error schema
    its endpoint returns for each status. Callers catch `ApiError`, and use
    `instanceof` on a subclass only when they need its extra fields.
  - To add an extension: the back adds it to its contract, run
    `npm run generate:types`, then add the subclass and its `code` mapping in
    `client.ts`.

## Back (BFF)

The back lives in another repository and acts as a _Backend for Frontend_:
every request from the front goes to it, and it calls the SpaceTraders API.

- The front only knows the back's contract, never the SpaceTraders API
  directly.
- The front calls the back directly, using the base URL from an
  environment variable (typed in `env.d.ts`). Front and back are different
  origins, so the back allows the front's origin through CORS; that config
  lives in the back's repository.

## Pending decisions

- Cross-origin cookies: when connecting the first endpoint that relies on the

  back's CORS must allow them. Neither does today.
- Internationalization (`vue-i18n` + `@intlify/unplugin-vue-i18n`): texts are
  in Spanish for now.
